# koko: 判定モデルの値に基づく、まとまりごとの推敲

日本語の文章を意味のまとまりに分け、まとまりごとに `koko-copy-editor` エージェントに推敲させます。あなた（メインエージェント）の仕事は、分割・指示・組み立て・継ぎ目の点検です。推敲そのものは koko-copy-editor に任せ、自分ではしません。

サブエージェントはサブエージェントを起動できません。このスキルは、メインエージェント（会話の本体）で動かしてください。

## 指標

- 判定モデルは、このスキルの `model/` に同梱しています（saihai-v1-8b をファインチューニングし、2bit に量子化したもの。約 2.6 GB。由来は `model/NOTICE.md`）。文体（丁寧体か、長さ、英字の有無）をそろえて学習した版なので、です・ます調かどうかに頼らず、話題や書きぶりで判定します。
- 入力は 1 文です。P(Yes) は、その文を Wikipedia 由来（人が書いた側）と判定する確率です。まとまりの値は、まとまり内の文の P(Yes) の単純平均です。目標は 0.9 以上です。
- 文の分け方と前処理は、モデルの学習データと同じです（`scripts/kokotext.py`）。採点は 1 文ずつ行い、同じ文にはいつも同じ値が付きます。新しい文は 1 秒に 4 文ほどです（GPU のとき）。
- 作業の報告や評価・結果の数値を述べる文は、どう言い換えても上がりにくいです。以前の実験では、Haiku に推敲させて目標に届いたのは 34 まとまりのうち 2 まとまりでした。届かないまとまりが出ることを前提に、結果は正直に報告してください。

## 道具

`<このスキルのディレクトリ>/scripts/koko.py` を、uv で動かします。以下では `KOKO="uv run <このスキルのディレクトリ>/scripts/koko.py"` と書きます。パスは必ず絶対パスにします。CLI は標準ライブラリだけで動き、採点サーバは依存の版をロックファイルで固定した uv のスクリプト（`scripts/serve_cu130.py`、`scripts/serve_cpu.py`）で動きます。

| コマンド | 内容 |
|---|---|
| `$KOKO doctor` | 動かす準備ができているかを調べる。1 行目が `koko-doctor: ready`（使える）、`needs_setup`（採点サーバの環境がない）、`unavailable`（モデルが壊れている、または uv がない） |
| `$KOKO setup` | 採点サーバの環境（torch、transformers など。版はロックファイルで固定）を uv で用意する。初回は数 GB をダウンロードすることがある |
| `$KOKO server start` / `status` / `stop` | 採点サーバの起動・確認・停止。モデルを GPU に 1 回だけ載せ（約 2.5 GiB）、並列のエージェントの採点をまとめて受ける。採点のときに自動で起動し、30 分使われなければ自動で止まる |
| `$KOKO blocks FILE --sentences --plan-out PLAN` | 文書をブロック（段落、箇条書き、見出し、表など）に分け、文ごとの P(Yes) を出す。まとまりの機械的な下書きを計画ファイルに書く |
| `$KOKO split --plan PLAN --workdir DIR` | 計画を検証し、まとまりごとの原文と、koko-copy-editor への指示書を書く |
| `$KOKO score FILE` | まとまりを採点する（`--variants` は「===」の行で区切った複数案、`--lines` は 1 行 1 案） |
| `$KOKO check ORIG REVISED` | 原文と推敲案の機械チェック（リンク、数値、インラインコード、括弧書き、長さ、文体） |
| `$KOKO assemble --plan DIR/plan.json [--out OUT]` | 推敲後のまとまりを文書に戻し（`--out` を省くと元のファイルを上書きする）、採点し直して `DIR/report.md` と記録 `DIR/record.json` を書く。まとまりの外は 1 文字も変えない |
| `$KOKO verify --workdir DIR` | `OUT` が、assemble で記録した本文のままかを確かめる。1 行目が `koko-check: ok` なら合っている |

`blocks`、`split`、`score`、`check`、`assemble`、`verify`、`doctor` は `--json` で機械向けの出力にできます。

## 手順

### 1. 準備

- `$KOKO doctor` を実行します。`needs_setup` なら、数 GB のダウンロードがありうることをユーザーに一言伝えてから `$KOKO setup` を実行します。`unavailable` なら、出力をユーザーに伝えて止めます。CUDA も MPS も使えないと出たときは、採点が CPU で動くこと（CPU での速さは確かめていないこと）を伝えます。
- 対象のファイルを確かめます。文章が会話に貼られただけなら、作業ディレクトリに `.md` として保存してから始めます。
- 作業ディレクトリ `WORK` は、指定がなければ現在のディレクトリの `.koko/<ファイル名の stem>/` にします。出力 `OUT` は、指定がなければ元のファイルです（**上書きします**）。元のファイルの写しは、手順 3 で `WORK/source.md` に残ります。上書きしたくないと、ユーザーか呼び出し元が求めたときだけ、別の `OUT` を指定します。
- 採点サーバを先に起動します: `$KOKO server start`。エージェントを並列で起動する前に起動しておくと、モデルの読み込みが重なりません。

### 2. 全体を読み、まとまりを決める

```bash
$KOKO blocks FILE --sentences --plan-out WORK/plan.json --style です・ます調
```

文書全体を Read で読み、`blocks` の出力（ブロックの行番号、文の数、P(Yes)）と合わせて、意味のまとまりを決めます。`WORK/plan.json` の下書きを直します。

- **境目はブロックの境目**（空行の位置）にします。1 つの段落の途中では切れません。見出し、表、コード、画像、HTML はまとまりに入れられず、そのまま残ります。
- **固定する行**: 図表のキャプション（`図1: …`、`表2: …` で始まる段落）は、既定で固定します（`protected`）。キャプションは図表の中身と対になっていて、図表を見られないエージェントが書き換えると、図表と食い違うおそれがあるからです。ほかにも変えてはいけない段落があれば、`--protect '<正規表現>'` で 1 行目の形を指定します。キャプションも推敲するときは `--no-default-protect` を付けます。
- **意味で区切ります。** 導入の文と直後の箇条書き、同じ話題が続く短い段落は 1 つのまとまりにします。話題の変わる所で分けます。目安は 2〜8 文です。小さすぎると構成を組み替える余地がなく、大きすぎると探索が散らばります。
- すでに目標以上のまとまりも計画に入れておきます（エージェントは起動しません）。

各まとまりに次を書きます。

```json
{
  "source": "/abs/path/doc.md",
  "target": 0.9,
  "style": "です・ます調",
  "protect": ["^(図|表)\\s*\\d+\\s*[:：.．]"],
  "chunks": [
    {
      "id": "c01",
      "lines": [5, 9],
      "section": "はじめに",
      "intent": "このまとまりで伝えたいこと（必須）",
      "prev_constraints": "前のまとまりと内容的に整合させる内容（空ならエージェントが補完）",
      "next_constraints": "次のまとまりと内容的に整合させる内容（空ならエージェントが補完）",
      "notes": "任意の補足"
    }
  ]
}
```

- `intent`（この複数文で伝えたいこと）は必須です。主張、結論、欠かせない事実や数値を具体的に書きます。ここにない細部は、エージェントが省いたり言い換えたりしてよいものとして扱われます。呼び出し元が文書の設計（各節の要点、主張の一覧、話の流れなど）を渡したときは、それを根拠にします。
- `prev_constraints` / `next_constraints` は、文書全体を見ているあなたが書くのが確実です。用語や呼び名の統一、指示語や接続詞が指す内容、前で述べた事実との矛盾がないこと、次のまとまりが前提にする内容（例: 次が「この結果から」で始まるなら、このまとまりの終わりで結果を述べる）、次で初めて述べる情報を先取りしないこと、などです。確信が持てなければ空にします。そのときはエージェントが前後を読んで補完します。
- `style` は文書の文体です。まとまりごとに違うなら、まとまりに `style` を書きます。

### 3. 切り出す

```bash
$KOKO split --plan WORK/plan.json --workdir WORK
```

計画に問題があれば、理由が出て止まります（ブロックの境目と合わない、固定のブロックを含む、`intent` が空、など）。直してやり直します。成功すると、`WORK/chunks/` に原文（`cNN.md`）、元の値（`cNN.orig.json`）、指示書（`cNN.brief.md`）ができます。計画を変えて切り出し直すときは `--force` を付けます（前の `chunks/` は `chunks.bak-<日時>/` に退避されます）。

### 4. koko-copy-editor を起動する

平均 P(Yes) が目標未満のまとまりごとに、`subagent_type: "koko-copy-editor"` でエージェントを起動します。プロンプトは次の形にします。

```
まとまり cNN を校閲してください。
指示書: <WORK>/chunks/cNN.brief.md
（伝えたいこと、前後との整合条件、原文、採点と出力の方法は指示書にあります。最初に読んでください。）
```

- エージェント 1 つの目安は 3〜10 分、数万〜10 万トークンです。起動するまとまりが 10 を超えるときは、先にその数と目安をユーザーに伝え、全部を推敲するか一部にするかを確かめます（呼び出し元が範囲を決めているときは、それに従います）。
- 一度に 4〜5 個まで、1 つのメッセージでまとめて起動します。終わったものから次を起動します。
- `koko-copy-editor` が使えるエージェントの一覧にない場合（定義ファイルを置く前に始めたセッションなど）は、`general-purpose` で起動し、プロンプトの先頭に「最初に `<プロジェクト>/.claude/agents/koko-copy-editor.md`（絶対パスにする）を読み、frontmatter より後の本文をあなたの役割の指示として従ってください。」と書きます。
- 並列のエージェントが見る前後のまとまりは原文です。そのため、整合条件は「何を伝えるか」という内容の水準で書いておきます（言い回しの一致は求めない）。
- エージェントの報告（値、補完した整合条件、省いた内容、上がらなかった文）は、そのまま信じず、次の手順の採点で確かめます。

### 5. 組み立てて採点し直す

```bash
$KOKO assemble --plan WORK/plan.json            # OUT が元のファイルのとき（既定）
$KOKO assemble --plan WORK/plan.json --out OUT  # 別の OUT を指定されたとき
```

元のファイルが split のあとに書き換えられていると（ユーザーが手で直したなど）、`assemble` は上書きせずに止まります。その変更を消さないように、手順 2 からやり直します。

推敲後の本文（`cNN.revised.md`）があるまとまりは置き換え、ないまとまりは原文のまま残します。報告（`WORK/report.md`）には、まとまりごとの前後の値、達成か未達か、機械チェックの結果、作業メモへのリンクが入ります。記録（`WORK/record.json`）には、`OUT` のハッシュとまとまりごとの値が入ります。

### 6. 継ぎ目を点検する

`OUT` を読み、まとまりの継ぎ目ごとに、前後のつながりを確かめます。用語の揺れ、指示語の指す先、同じ情報の重複や抜け、文体の揺れ（です・ます調とである調が混ざっていないか）です。あわせて、各まとまりの作業メモの「省いた・言い換えた内容」を読み、文書全体で欠けてはいけない情報が落ちていないかも確かめます。

点検するのは、つながりと内容だけです。文が自然かどうか、読みやすいかどうかを、あなたの感覚で判断して直したり、報告に書いたりしません。その判断は判定モデルの値と、文書を読む人に任せます。

問題があるまとまりは、同じ指示書でエージェントを起動し直します。直すべき点（例: 「直後のまとまりは推敲後、『〜』で始まります。それに合わせて、このまとまりの終わりで〜を述べてください」）をプロンプトに書き足します。終わったら手順 5 をやり直します。あなたが自分で本文を直すのは、つながりの問題を直すときだけです。その場合も、`chunks/cNN.revised.md` を直してから、必ず `assemble` で採点し直します（`OUT` を直接直すと、`verify` が `modified` になります）。

### 7. 報告する

- 出力のパス（`OUT`）、報告のパス（`WORK/report.md`）、記録のパス（`WORK/record.json`）
- 目標を達成したまとまりの数、文書全体の平均 P(Yes) の前後
- 未達のまとまりと、上がらなかった理由（作業メモから）
- 省いたり言い換えたりした内容のうち、確かめたほうがよいもの
- 継ぎ目の点検で直したこと

推敲後の本文は、報告に載せません（ファイルにあります）。続けて未達のまとまりを詰めたいかは、ユーザーに選んでもらいます。元に戻したいときは、`WORK/source.md` が元のファイルの写しです。作業が終わったら、`$KOKO server stop` で GPU を空けます（続けて使うなら止めなくてよい）。

## ほかのスキルやワークフローから呼ばれたとき

次のように振る舞います。入出力の取り決め（渡せるもの、できあがるファイル、`record.json` の形、`verify` の終了コード）は [references/interface.md](references/interface.md) にあります。

- **入力は呼び出し元に従う**: 原文、`OUT`、`WORK`、文体、固定する段落（`protect`）、目標、対象にするまとまりの範囲、文書の要点（`intent` の根拠）、全体への補足（計画の `notes`）を受け取ります。指定のないものは、手順の既定を使います。
- **ユーザーに直接聞かない**: 手順 4 の確認（まとまりが 10 を超える）と手順 7 の選択は、呼び出し元が範囲を決めていればしません。判断が要ることは、報告の「呼び出し元に確かめたい点」にまとめて返します。
- **書くのは `OUT` と `WORK` だけ**: `OUT` の既定は原文です（上書き）。原文を書き換えたくない呼び出し元は、別の `OUT` を指定します。
- **完了の確かめ方**: 呼び出し元は `$KOKO verify --workdir WORK --final OUT` の終了コード（0 が ok）か、1 行目の `koko-check: <状態>` で、`OUT` が koko で採点した本文のままかを確かめられます。値は `WORK/record.json` の `summary` にあります。
- **動かせないとき**: `$KOKO doctor` が `ready` でなければ、推敲を始めず、`doctor` の出力をそのまま返します。

## 設定

環境変数で変えられます。

| 変数 | 既定 |
|---|---|
| `KOKO_TORCH` | 採点サーバの torch の種類。`nvidia-smi` があれば `cu130`、なければ `cpu`（macOS では、MPS を使える PyPI の torch が入る） |
| `KOKO_STATE_DIR` | 採点サーバの状態とログの置き場所。`$XDG_RUNTIME_DIR/koko`、なければ一時ディレクトリの `koko-<uid>` |
| `KOKO_MODEL` | このスキルの `model/` |
| `KOKO_DEVICE` | CUDA が使えれば `cuda`、次に MPS（Apple Silicon の GPU）が使えれば `mps`、どちらもなければ `cpu` |
| `KOKO_IDLE_SECONDS` | `1800` |
| `KOKO_FAKE_SCORER` | なし（`1` で、モデルを使わずに仮の値を返す。テスト用） |
